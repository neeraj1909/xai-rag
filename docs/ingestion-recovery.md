# Host-local ingestion recovery

Before starting any writer, an operator must pre-provision the journal root on a persistent local filesystem, with durable directory entries and mode `0700`; the application does not create this root. Set `XAI_RAG_INGESTION_JOURNAL_ROOT` to this same absolute, private directory for **every** API and CLI writer of the same indexes. An empty value disables the journal. Provision and back up this directory under the service account, and mount it persistently when using containers. Its parent and ancestors must be service-controlled. The directory contains full source documents with restrictive permissions; pending documents remain there indefinitely until replay succeeds or an operator handles the incident. Unlinking is not secure erasure; follow your data retention policy and protect backups.

The journal namespaces each intent using the configured Chroma endpoint and collection, Elasticsearch endpoint and index, and tenant. All writers must use identical canonical endpoint configuration and this journal root: aliases for the same backend, another host, direct store writes, and another journal directory can bypass the lock. Configured endpoints must match injected client connections. This POSIX local-file lock is not a distributed lease or cross-store transaction; queries can observe partial updates while a write is incomplete. Whole-index parity can race writes from other processes.

On interruption the intent and exact staged bytes remain on disk. New journaled writes for that namespace stop while the intent exists. Before recovering, an operator must stop all old writers **and establish that any already-sent remote requests have finished**; a process exit or timeout alone does not establish this. There is no backend fencing for requests that arrive late.

For a scoped tenant, load the current authorization policy and set the authorized ingester's key in `XAI_RAG_INGEST_API_KEY` without exposing it in shell history. With the same store settings and journal root, run:

```sh
xai-rag recover-ingestion --acknowledge-quiescence
```

Recovery checks the current grant for the original relative source, requires the same tenant and configured index namespace and embedding fingerprint, re-parses the journaled bytes, and checks that the recomputed record manifest matches the saved manifest. It rewrites both stores, then verifies actual content and full metadata against that manifest before removing the intent. A revoked grant observed before the command blocks replay; revocation racing an already-authorized replay is not fenced. Parser/chunker changes can cause the manifest check to fail; restore the original configuration or investigate manually. A corrupt intent or a missing/corrupt snapshot referenced by an existing intent fails closed and needs operator investigation. If a marker is externally lost, the application cannot distinguish that loss from no pending work; protect and monitor the journal volume. Do not delete pending state merely to resume service: the indexes may be inconsistent.

The CLI's `validate-indexes` compares actual stored text and metadata in both indexes. In scoped mode it requires an authorized ingester credential and an explicitly granted `--source`. Parity alone does not prove that both stores contain the intended version; recovery checks the intended manifest too. Neither check proves embedding vector correctness.

For the optional Compose overlay, explicitly provision a host directory owned by the container service UID `10001` and mode `0700`, then set `XAI_RAG_JOURNAL_HOST_DIR` to its absolute path and start with `docker compose -f docker-compose.yml -f docker-compose.journal.yml up`. The overlay binds this directory at `/var/lib/xai-rag-journal` and enables the journal. Provisioning and retaining that sensitive directory is an operator responsibility. Run recovery inside the same configured container so endpoint identities and the journal path match; stop other writers and establish remote quiescence first. This overlay does not coordinate writers on other hosts.
