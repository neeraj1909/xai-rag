A guardrail is a control with a defined boundary and failure policy. It can reject an invalid request, constrain what reaches a model, or produce evidence for a decision. It does not automatically guarantee that an answer is correct or that a system is safe.

## The problem and the boundary

A document-grounded assistant accepts user questions and ingests files, searches two indexes, sends selected text to a model, and may score claims with an NLI model. Each crossing has a different risk:

```text
caller → authenticate + validate + per-process quota
       → authorized source? → dense / lexical retrieval
       → bounded, delimited source text → LLM → citation contract
       → optional NLI / RAGAS diagnostic → answer and trace

operator → allowed path → bounded discovery + parser → Chroma and Elasticsearch
```

The shared API key authenticates the service caller; **it does not identify a tenant or grant document-level permissions**. In `f4c374d`, prompt instructions tell the LLM that source documents are untrusted; the optional NLI result is diagnostic, and streaming can emit the answer before that diagnostic. See the [original API](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/api/app.py), [generator](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/generation/generator.py) and [service](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/service.py).

## Interview questions with answers

### 1. What is the difference between a prompt instruction and a guardrail?

**What:** A prompt instruction asks the model to follow a policy; a code-enforced guardrail checks or limits an observable condition at a boundary. **Why:** A model can misunderstand or ignore text, and retrieved documents can contain competing instructions. **How:** This project labels source text as untrusted, bounds context and validates citation IDs. The `c375903` delimiter encoding stops a document from creating a literal new wrapper, but it does not prove the model will ignore an instruction inside an otherwise valid wrapper. Evaluate that separately with adversarial passages and legitimate controls.

### 2. How does the citation fix work, and what does it not prove?

**What:** Context construction records the chunks actually included in the prompt. **Why:** A ranked result outside the prompt can have a valid database ID but still be unseen by the answering model. **How:** Validation checks inline and structured source IDs against the included IDs; if no nonblank evidence fits, generation abstains. A chunk with only a visible prefix remains citable, so also test whether the **specific visible text** supports each claim. An ID resolving to a record is provenance syntax, not semantic entailment or an authority check.

### 3. Why must the NLI checker receive the same evidence as generation?

**What:** NLI compares a claim with a premise and returns support-related scores. **Why:** If the premise contains a sentence that the generator never received, the checker can report support from unavailable evidence. The reverse can happen if generation received parent text but the checker sees only a child. **How:** The `c375903` change carries a per-request snapshot of the prompt-visible prefix, avoiding a shared mutable “last prompt.” RAGAS receives the literal escaped text; NLI receives a copy decoded exactly once. This restores source characters such as `<` without adding an omitted suffix; a literal source `&lt;` remains `&lt;` after one decoding pass. A small real DeBERTa probe found that entity encoding changed some entailment scores, so this normalization is a measured design choice, not proof of how the LLM interpreted the text. Test truncation, parent/child differences, escaping and simultaneous requests; NLI remains an imperfect diagnostic.

### 4. Why not simply let the faithfulness model block every unsafe answer?

**What:** The current NLI is an optional diagnostic, not a release gate. **Why:** It can misread negation, numbers or encoded text, and a neutral result is not the same as contradiction. Uncalibrated automatic blocking can also reject correct answers. **How:** On a representative, independently labelled set, measure false acceptance, false refusal and disagreement by case type. If the product requires checked output, define an explicit supported / contradicted / neutral / unavailable policy, then buffer answer text until the policy is satisfied. Existing SSE can emit generation before the diagnostic, so a later warning cannot retract what the user already saw.

### 5. What happens if a client times out while a local model is still running?

**What:** An `asyncio` timeout cancels a coroutine, not native work that has already started in a thread. **Why:** Releasing the concurrency semaphore too early lets repeated timed-out requests accumulate more active work than the nominal limit. **How:** The `c375903` mechanism keeps admission with the worker until started thread work completes, then stops the cancelled pipeline before a later stage. A query can return its timeout promptly while cleanup continues. A thread that never returns requires process-level supervision and a restart policy; this mechanism cannot kill it.

### 6. How do file-size controls handle a compressed document?

**What:** DOCX is a ZIP-based format; small compressed bytes can represent much larger expanded content. **Why:** A compressed-size limit alone does not bound memory and CPU consumed by the parser. **How:** Before parsing, the `c375903` implementation adds the declared uncompressed member sizes and rejects a total above `max_document_bytes`. Test a compressed bomb-like synthetic file and a legitimate file under the boundary. Treat this as one resource control: hostile files may also need isolated parsing, CPU/memory limits and an explicit trust policy.

### 7. Can an API key and citation check isolate customer data?

**What:** Neither establishes per-user document permissions. **Why:** The existing key is shared, and a document may already reach a model before a citation is generated. **How:** A production design must authenticate a caller, resolve permitted document scope server-side and apply it to **both** the Chroma and Elasticsearch paths before fusion, reranking and generation. Include parent context, caches and failure/fallback paths. Use cross-tenant negative tests. This is a proposed authorization design, not functionality claimed by the current patch.

### 8. How will you test guardrails without overstating the results?

**What:** Treat a control as a falsifiable contract with cases and a failure denominator. **Why:** A single successful adversarial prompt or a high judge score cannot prove resistance, and a model judge can be wrong. **How:** Run the [fictional cases and protocol](guardrail-evaluation-plan.md), record actual prompt-visible evidence, outputs, errors and exclusions, and compare against independent human review where available. Report attack success and legitimate-question false refusal separately. Keep no-evidence, conflicting-source, injection, invalid citation, boundary and dependency-failure tests distinct. Do not claim human evaluation unless a person actually reviews the outputs.

### 9. Which limitations would you disclose before production?

No per-document or tenant ACL is established; API quotas are process-local; prompt encoding cannot eliminate injection; NLI is not a mandatory release gate; SSE can release answers before optional diagnostics; indexes can diverge across partial writes, cancellation or crashes despite the event-loop-local ingestion lock; and DOCX/parser controls do not eliminate malicious files or path races. A user able to mutate the ingestion root between discovery and parsing may be able to replace a path. A production threat model needs a trustworthy ingestion source or a race-resistant file-opening design, parser isolation, and tests for multiworker coordination, backup, recovery, and authorization. The precise sequence should follow the deployment's real trust and risk requirements.

### 10. What should a readiness endpoint do when a search dependency hangs?

**What:** Readiness tells an orchestrator whether this process can currently serve requests; a failed dependency produces HTTP 503. **Why:** A health check that waits indefinitely can itself exhaust resources and hide an outage. **How:** Revision `c375903` gives Chroma and Elasticsearch separate two-second budgets and checks them in sequence. It shares the in-flight Chroma heartbeat so repeated checks do not start unbounded threads after timeouts. This is not an overall two-second deadline: both timeouts can add up to roughly four seconds plus overhead. An indefinitely stuck native thread cannot be killed by the timeout; the probe stays degraded until the operation ends or the process is restarted. A separate liveness endpoint and process supervision are therefore still necessary.

### 11. Why refresh after deleting a source in Elasticsearch?

**What:** A successful delete and search visibility are distinct: a search can temporarily see old documents before refresh. **Why:** In the empty-chunk or source-deletion path, stale search hits could survive the delete and produce misleading retrieval or parity results. **How:** Revision `c375903` asks `delete_by_query` to refresh on completion. A controlled real Elasticsearch test with automatic refresh disabled saw the old delete leave a count of 1 until explicit refresh, while the patched delete returned a count of 0 immediately. This establishes the observed search-visibility behavior in that setup, not a cross-store transaction or a production performance benchmark. At scale, compare the refresh cost with the visibility requirement and design explicit recovery for Chroma/Elasticsearch partial failures.

### 12. Does a post-parse character limit make document parsing safe?

**What:** Revision `c375903` limits each extracted Python string to 20 million characters by default, configurable through `XAI_RAG_MAX_EXTRACTED_CHARACTERS`. **Why:** A small file can yield a much larger extracted string, making chunking and embedding expensive even when input bytes passed their limits. **How:** Ingestion parses first, then rejects text longer than the configured limit before chunking or embedding; text exactly at the limit passes this check. A unit test injects four- and five-character parser results at a limit of four. This cannot prevent memory or CPU consumption during parsing itself. For untrusted documents, separately isolate the parser and enforce operating-system resource and time limits.

### 13. Which model endpoint is used when no project endpoint is configured?

**What:** Generation in `c375903` and RAGAS client construction use `XAI_RAG_LLM_BASE_URL` when set, otherwise explicitly use `https://api.openai.com/v1`. **Why:** An implicit generic SDK environment variable could silently route those clients to a different endpoint. **How:** The fallback is passed as the client `base_url`, so `OPENAI_BASE_URL` no longer selects the endpoint for these constructed clients. Configure the project-specific variable explicitly for a compatible provider. This is a behavior change for deployments that previously relied only on `OPENAI_BASE_URL`; check separately configured or injected clients rather than assuming every model connection follows this rule.

### 14. How do you reduce sensitive information in API errors and logs?

**What:** The `c375903` API returns a fixed validation error and suppresses the underlying provider exception chain on startup failure. The provided `make serve` command disables Uvicorn access logs. **Why:** Invalid requests, startup exceptions and URL logs can contain document names, submitted text or provider details. **How:** Canary tests verify that selected query and ingest validation inputs, arbitrary validation details and a simulated provider secret do not appear in the tested response or formatted startup traceback; a separate test checks the Makefile flag. The tradeoff is that a client receives no per-field explanation in a 422 response. This is not a complete privacy guarantee: other launchers and reverse proxies may still log the `source_path` query parameter, and the ingestion response deliberately includes `source_file`. Review those configurations and response access separately.

### 15. Why limit semantic units as well as extracted characters?

**What:** Semantic chunking turns sentences, or bounded pieces of a long sentence, into units for a sentence-embedding model. The `c375903` limit defaults to 10,000 units and can be set with `XAI_RAG_MAX_SEMANTIC_UNITS`. **Why:** A character limit alone may allow an excessive number of short units and therefore expensive model input. **How:** The chunker counts units while building them and rejects an over-limit document before loading the model. Focused tests check three short sentences against a limit of two; a 30-character sentence split into ten-character units against a limit of two; and three units at a limit of three, where an injected model runs and source offsets are preserved. Sentence spans are now yielded lazily so an over-limit document can stop early; the already completed PDF parsing can still allocate memory and consume CPU before this guard. Protecting parsing needs separate resource isolation and limits.

### 16. Who owns the RAGAS evaluation client?

**What:** The default scorer factory constructs an asynchronous model client for evaluation; a caller can instead supply a scorer factory. **Why:** A client left open can retain connections, while closing a shared client supplied by someone else can break that caller. Metric tasks may also still be running when another metric fails. **How:** The `c375903` adapter cancels unfinished metric tasks and awaits their completion before closing the default factory's owned client. If default scorer setup fails after client construction, it attempts to close the client there too. An injected scorer factory keeps ownership of its own client. Unit tests use controlled tasks and clients to exercise success, failure, cancellation and setup failure; this is lifecycle evidence, not a live-provider reliability result.

### 17. How should a client distinguish a search outage from a query failure?

**What:** The `c375903` query API classifies Elasticsearch connection errors and connection timeouts as dependency outages. **Why:** A dependency outage, a request timeout and an unexpected application error need different operational responses. **How:** REST returns HTTP 503 with a generic dependency message for the Elasticsearch connection exceptions; generic `TimeoutError` returns 504; unexpected exceptions return 500. The streaming route reports the corresponding problem in an SSE `error` event (`dependency_unavailable`, `timeout`, or the unexpected exception type), since the HTTP response may already have started. Controlled tests inject each category; they are not a new live outage measurement.

Ingestion has a separate contract: a successful batch returns 200, a partial batch 207, and a failed batch 500. Its per-document failures retain exception **type strings**, not full exceptions, so the endpoint cannot reliably infer from those strings that an Elasticsearch outage caused the batch failure and does not claim to return 503 for it. Parity failure can also affect batch status. The earlier soak's observed REST 500 remains the result for that earlier snapshot; this new classification does not rewrite that observation.

### 18. How do you bound chunk output across strategies?

**What:** Revision `c375903` caps the number of chunks per document at 100,000 by default through `XAI_RAG_MAX_CHUNKS_PER_DOCUMENT`. **Why:** A small configured chunk size or long input can produce enough chunks to overload later embedding and indexing. **How:** Fixed splitting checks spans as they are made; parent-document splitting also caps children; semantic splitting checks grouped output after its model step, with a separate 10,000-unit default cap on that model input. Tests exercise fixed and parent-document limit boundaries, excessive children from one parent, and semantic grouped output. Lazy sentence iteration also allows semantic unit rejection without first materializing every sentence span. In one captured 300,000-character synthetic case, peak traced allocation fell from about 18.7 MB to under 3 MB; this is one measurement, not a general memory guarantee. Parsing remains earlier and is not CPU- or memory-isolated by these controls.
