## Current implementation

### 1. What databases does XAI-RAG actually use, and why two?

**Answer:** Chroma stores embeddings, text and metadata for dense nearest-neighbour retrieval; Elasticsearch stores text and metadata for BM25 lexical retrieval. The two searches return a common chunk ID, so reciprocal-rank fusion can combine and deduplicate their results before reranking. Dense search can find paraphrases, while BM25 can surface exact names or identifiers. Two indexes add ingestion, consistency and operations costs; measure whether the combined recall justifies them for the actual workload. [Vector search](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/retrieval/vector_search.py), [BM25](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/retrieval/bm25_search.py).

### 2. Is Chroma an embedded in-process database here?

**Answer:** No. The API and ingestion code use `chromadb.HttpClient` to reach the Chroma server. The local Compose stack maps server ports to loopback and mounts separate named volumes for Chroma and Elasticsearch. The volume preserves local data across ordinary container recreation, but does not itself prove a tested backup, high availability or disaster recovery. The code's Chroma collection is configured for cosine distance. [Store setup](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/ingestion/store.py), [Compose](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/docker-compose.yml).

### 3. What happens when one document is indexed?

**Answer:** The service resolves a source identity, parses and chunks the file, embeds its chunks, then calls the Chroma writer first. That writer generates deterministic IDs and upserts vectors, documents and metadata. Only after it returns does the service bulk-index the same IDs and text in Elasticsearch. Elasticsearch checks item-level bulk errors and then removes obsolete IDs for that source. The service records a per-file outcome and performs a parity check after the batch. Those steps are separate operations, not one transaction. [Ingestion orchestration](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/service.py), [storage](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/ingestion/store.py).

### Follow-up: How does a CLI file keep its identity under a common root?

**Answer:** In `c375903`, `xai-rag ingest /docs/nested/doc.txt --document-root /docs` uses `nested/doc.txt` as the relative source identity. Without the option, the CLI still defaults to the file's parent, so choosing different roots can produce different identities. Choose and persist a stable root; the option does not automatically remove older duplicate identities.

### 4. How are chunk IDs generated? Does rerunning ingestion duplicate the data?

**Answer:** The ID is a SHA-256 of a canonical JSON identity containing the ID schema version, source path identity, chunk index, character offsets, chunking strategy and chunk content. Reprocessing unchanged inputs produces the same ID; Chroma `upsert` and Elasticsearch `index` with that ID support retry without creating another ID for the same chunk. A changed path, boundary, strategy or content creates a different ID. This is per-record idempotence, not an exactly-once guarantee for an entire ingestion job or its effects across stores. [ID and writes](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/ingestion/store.py).

### 5. What happens when an existing document changes?

**Answer:** Within each store, the code writes the current IDs and deletes previous IDs for the same `source_file` that are absent from the current set. For example, if a paragraph edit changes chunk `A` to `B`, Chroma first upserts `B` and deletes old `A`; Elasticsearch then indexes `B` and deletes stale `A`. A failure or cancellation between these stages can leave a temporary or persistent discrepancy. At baseline, concurrent jobs could interleave cleanup. Revision `c375903` serializes entire ingestion batches within one event loop, including discovery, writes and parity checking; it deliberately serializes even different sources. Other event loops and processes remain uncoordinated, and a parity scan is not a cross-process snapshot. For multiple workers I would add durable versioned coordination and test interleavings. An empty parsed chunk list also reaches the source cleanup path, so a robust product should distinguish a deliberately empty document from parser failure before removing a prior good version. [Storage](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/ingestion/store.py), [service](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/service.py).

### 6. What if the Chroma write succeeds and Elasticsearch fails?

**Answer:** Chroma may contain the new version while Elasticsearch still contains an old or partial version. The per-document outcome records failure and the batch checks index parity; successful documents plus a failure yield a `partial` batch, while a batch with no successes yields `failed`. There is no rollback or automatic repair in this path. Retrying the same unchanged source can converge in ordinary failure cases, but operators still need to investigate concurrent writes, delete-by-query conflicts and downstream failure rather than assuming a retry always fixes them. [Ingestion outcomes](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/service.py).

### 7. What does the parity check prove, and what does it miss?

**Answer:** It compares sets of IDs and the stored `content_sha256` metadata for matching IDs; Elasticsearch records are paged with `search_after`. It reports missing IDs and differing stored hashes. It does not recompute hashes from all stored document text, compare embeddings, check access permissions, guarantee a consistent snapshot while writes occur, or fix the indexes. If the parity check itself raises, the ingestion result reports `parity_consistent=false`; that outcome alone does not distinguish proven drift from inability to read a store. At large scale, scanning all Chroma metadata and Elasticsearch records can be expensive; measure and design incremental reconciliation. [Parity implementation](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/ingestion/store.py), [ingestion result](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/service.py).

### 8. Can the application delete a document from both databases today?

**Answer:** There are separate helper functions for deleting a source from Chroma and Elasticsearch, and reingesting an empty chunk set invokes cleanup. The inspected service does not expose a coordinated, durable cross-store deletion workflow. Production deletion would need a user-authorized operation, a durable tombstone or deletion job, retry tracking for both indexes, cache invalidation and verification that removed text cannot be retrieved. Decide retention and backup-deletion obligations explicitly. [Storage helpers](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/ingestion/store.py).

### 9. What happens if I change the embedding model?

**Answer:** The index fingerprint includes the chunk-ID schema version, embedding model name and revision, vector dimension and cosine distance. Existing collection/index fingerprints are checked before use; a missing or incompatible fingerprint on a populated store raises a compatibility error. This prevents silently treating incompatible vectors as the current model. It does not by itself rebuild the index or track every ingestion setting, such as all chunking parameters. Create a new versioned collection and lexical index, re-embed the source corpus, compare retrieval and cut over only when both are ready. [Fingerprint code](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/ingestion/store.py).

## Production decisions

### 10. Can we keep Chroma in production, or must we replace it?

**Answer:** Keep it as a candidate if a supported deployment meets the actual corpus size, latency, throughput, security, availability, backup and operating requirements. The existing HTTP-client boundary makes an independently operated Chroma server a natural starting point; it does not establish that this local Compose server is production-ready. Benchmark realistic ingest/query concurrency and filtered recall; verify version-specific authentication, network isolation, backup/restore, updates and support. Consider an alternative only when a measured requirement or ownership constraint is not met. Elasticsearch may remain the lexical store, or a tested alternative could provide both dense and lexical retrieval; either change must preserve the application's IDs, filters, ranking and evaluation contracts. [Chroma client modes](https://docs.trychroma.com/docs/run-chroma/clients).

### 11. What specific changes are needed for multi-tenant retrieval?

**Answer:** Today the endpoint API key does not bind a query to an end user, and neither `vector_search` nor `bm25_search` accepts an authorization filter. Chroma metadata has no tenant field in the inspected schema; Elasticsearch stores `metadata` with indexing disabled, so adding a nested tenant field there alone would not make it searchable. I would authenticate the user, resolve permitted tenant/document IDs server-side, store queryable authorization fields or select an appropriate isolated index/collection, and enforce equivalent pre-retrieval filters on **both** paths. Test adversarial IDs, revoked access, no-filter regressions and cached contexts. Chroma's `where` filter is a filtering mechanism, not a substitute for a trusted authorization layer. [Current search paths](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/retrieval/vector_search.py), [ES mapping](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/ingestion/store.py), [Chroma metadata filtering](https://docs.trychroma.com/docs/querying-collections/metadata-filtering).

### 12. How would you deploy the two indexes securely?

**Answer:** Keep both services on private networks, authenticate service-to-service access, encrypt traffic where it crosses a trust boundary, restrict credentials and protect backups. The development Compose file deliberately binds stores to loopback; its Elasticsearch has security disabled, one node and zero replicas. The code can pass an Elasticsearch API key, but configuring a key does not prove the deployed server enforces access or that Chroma has equivalent controls. Verify Chroma transport/authentication support and client configuration for the chosen version; the inspected `HttpClient` call supplies only host and port. Test denied access from an unauthorized process and credential rotation. [Compose](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/docker-compose.yml), [client setup](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/ingestion/store.py).

### 13. How would you rebuild without serving a mixed index version?

**Answer:** Propose a version manifest containing a matching Chroma collection, Elasticsearch index, embedding model and corpus snapshot. Build both new stores from the authoritative source, then validate per-source IDs/hashes, retrieval quality and authorization before routing requests to the new manifest. Route each request using one manifest snapshot so it cannot mix an old Chroma collection with a new lexical index. Keep the old pair for rollback and coordinate any updates that arrive during the build. An Elasticsearch reindex operation can copy its documents, but it neither regenerates new embeddings nor atomically switches Chroma and Elasticsearch together. This paired cutover is a proposed application-level design. [Elastic reindex reference](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reindex-indices).

### 14. What if one retrieval store becomes unavailable?

**Answer:** The current query path awaits both retrievers with `asyncio.gather`; it has no explicit single-store fallback and a failed branch can fail the request. Decide whether the product should fail closed or return a clearly labelled degraded result. If fallback is acceptable, preserve the same authorization filters, set a dependency deadline, mark which retrieval path ran, alert operators and compare quality on a labelled outage set. Do not silently imply that lexical-only retrieval has the same recall as hybrid retrieval. [Query orchestration](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/service.py).

### 15. What would you use as a source of truth and how would you recover drift?

**Answer:** I would retain the original authorized document and immutable version metadata in a durable source store, with an ingestion ledger recording target index version, content hash, job attempt and each store's state. A worker retries idempotent writes and a reconciler checks source versions against both indexes; persistent mismatch raises an alert and blocks or marks affected data according to policy. A later attempt must not let an older job delete the newer version. Test a process crash after each write, out-of-order updates, duplicate delivery and store recovery. This ledger and repair flow are proposals, not current functionality.

### 16. How would you measure whether the database design is good enough?

**Answer:** Freeze representative documents and labelled questions, including exact IDs, paraphrases, tenant-restricted content, updates and no-answer cases. Compare vector-only, BM25-only, fusion and reranking on the same questions using Hit@k/Recall@k and per-query regressions; measure authorization leaks as zero-tolerance test failures. At stated corpus size and concurrency, capture ingestion throughput, per-store errors, p50/p95 retrieval latency, memory/disk, cost and recovery time. Run partial-write, restart, backup-restore, update/delete and simultaneous-ingest tests. A passing synthetic fixture checks behavior; it does not establish production relevance, capacity or security.

### 17. Is an Elasticsearch replica or a named volume sufficient for recovery?

**Answer:** No. Replicas can improve availability under certain node failures, but they also replicate bad writes and deletes; a volume only preserves what is on that storage. Define recovery-point and recovery-time targets, take version-appropriate backups of source documents and index metadata, and rehearse restoration into an isolated environment. Confirm both indexes match the same source/version manifest and re-run access and retrieval checks before routing traffic. The current single-node, zero-replica local Compose configuration is not a measured high-availability design.
