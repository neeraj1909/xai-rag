# Real-store crash/replay on the final development source

On 20 November 2026, the journal test was repeated after the directory-fsync repair on the then-current development source. It used a pre-provisioned private journal and disposable local Chroma and Elasticsearch services. A child exited with code 29 after the Chroma write and before the Elasticsearch write. The original document was changed; a fresh process replayed the saved original bytes and checked actual stored content and metadata: one record in each store, consistent with the intended snapshot.

`source-before.sha256` and `source-after.sha256` match byte for byte; they record individual Python-source file digests for this run, not a complete deployment snapshot. `run.txt`, `recover.log` and `cleanup.txt` record the outcome and names of the owned containers. `remaining-ports.txt` is empty after the cleanup check. This is a single forced failure boundary, not evidence of power-loss survival, delayed-remote-write fencing, atomic reads, vector correctness, multi-host safety, or a complete disaster recovery procedure.

The disposable Elasticsearch service needed a 60-second test client timeout and the transient `disk-watermark-override.json` setting because the shared host was over the allocation watermark. The override was confined to that test cluster; it is not a deployment recommendation. The sensitive journal data and the large container logs are not archived. The selected records were checked for common token patterns and configured secret values, without printing those values; this is not a comprehensive privacy guarantee.
