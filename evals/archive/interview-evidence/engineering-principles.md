## What should we keep, and what should change?

| Design decision | Evidence and risk | Smallest useful next step and verification |
| --- | --- | --- |
| **Keep one query pipeline behind the HTTP interface.** | Both `/query` and `/query/stream` call `RAGService.query`; its constructor accepts replaceable collaborators. This allows fast workflow tests without creating two independently maintained query paths. The constructor has many injected dependencies, however; adding another abstraction around every function would increase navigation without automatically reducing complexity. [API](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/api/app.py), [service](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/service.py). | Keep the shared path; introduce a narrower component only when a concrete change or ownership boundary benefits from it. Verify equivalent behavior with service tests and an HTTP test for each endpoint. [Service-layer trade-offs](https://www.cosmicpython.com/book/chapter_04_service_layer.html#chapter_04_service_layer_tradeoffs). |
| **Keep stable chunk identities and index checks.** | Ingestion uses deterministic IDs, replaces stale chunks, checks embedding-index compatibility and compares record parity. These are useful replay and diagnosis mechanisms, but they do not make both stores one transaction. [Storage code](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/ingestion/store.py). | Keep them while designing a durable ingestion manifest and reconciliation for each document version. Verify repeat ingestion, changed content and index-compatibility failure, then test concurrent ingestion and restart recovery. The existing [dual-store test](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/tests/integration/test_dual_store.py) exercises actual stores and deterministic vectors; it is not a model-quality test. |
| **Do not hide a distributed write behind an “atomic” wrapper.** | `ingest` writes Chroma first and Elasticsearch second, catches per-document failures and then checks parity. A failure between writes can leave partial state. Reporting partial/failed is valuable but does not reverse the completed write. [Ingestion path](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/service.py). | Store the intended document/index version and per-store status durably, retry idempotently, reconcile divergent writes and expose an incomplete version as unavailable until the chosen publish condition holds. Inject an Elasticsearch failure immediately after the Chroma write and test retry after process restart. A [unit of work](https://www.cosmicpython.com/book/chapter_06_uow.html) models a transaction within its real boundary; naming a class `UnitOfWork` would not make two independent databases atomic. |
| **Make the retrieval failure policy explicit.** | Dense and BM25 searches are awaited together with `asyncio.gather`. An uncaught branch error fails the query rather than automatically returning results from the other branch. [Query path](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/service.py). | Decide whether a product should fail closed or return a visibly degraded single-branch result; either choice changes coverage and reliability. Test each store's timeout and error, both-store failure, response contract, and retrieval/answer quality when degraded. Do not claim fallback until implemented and measured. |
| **Define the release point for evidence checks.** | The service emits a `generation` event containing the answer before its optional faithfulness report. The report is diagnostic in this implementation; it cannot retract text already received by a streaming client. [Event order](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/service.py). | If the use case requires a support check before display, buffer the candidate, apply the selected check, and emit an approved response or safe refusal. Test emitted event order, check failure, timeout and uncertainty. Measure added time to the first useful answer and evaluate false approvals and false refusals. |
| **Do not confuse a local control with a fleet-wide guarantee.** | API authentication uses a configured key, and its rate buckets and concurrency semaphore are held in process memory. They are useful local guards; they do not provide per-user authorization or a shared multi-replica quota. [API controls](https://github.com/neeraj1909/xai-rag/blob/f4c374d51d090beba61d34aba81fcc23b8ef700a/src/xai_rag/api/app.py). | For a multi-user service, authenticate users and enforce document access before retrieval, then choose a shared quota mechanism if replicas need a common budget. Test cross-tenant queries, revoked credentials and simultaneous requests across workers; never use a model-generated tenant ID as authority. |

## Interview follow-ups

**Q. Why use a service layer here?**

**A.** It gives the ordinary and streamed HTTP endpoints a common workflow, while letting tests replace external operations. The benefit is consistency and testability; the cost is another abstraction and a growing constructor. I would preserve this boundary and only split responsibilities when a demonstrated change or test problem justifies it.

**Q. How do you repair a failed ingestion?**

**A.** Today the service reports document outcomes and index parity; it does not guarantee automatic recovery. I would record a versioned job and each store's result durably, retry with stable chunk IDs, reconcile both indexes and publish only a completed version. I would test failure after the first write and recovery after restart.

**Q. Can the faithfulness report guarantee that no unsupported answer reaches a user?**

**A.** No. It is optional and runs after the generation event is emitted. Even a pre-release NLI check could make mistakes; I would evaluate it on human-labelled supported, unsupported, contradictory and insufficient-evidence cases and define the policy for uncertainty.
