# XAI-RAG hardening: evidence and limits

These are different experiments, not one end-to-end benchmark. Their source, fixtures and execution boundaries matter. This page is a reading aid; check the [archived synthetic fixtures, results and selected logs](evaluation/hardening-2026-11-20/README.md) and execution environment before attempting to reproduce results. No independently human-labelled evaluation is reported here.

## Repeated seeded HTTP and RAGAS evaluation

On 20 November 2026, a later evaluation ran the same 40 fictional questions three times against one scoped index and the expanded grounding judge. Both the case-order and evaluation-wrapper chat request seeds were `20261120`; embedding calls were not seeded. After one separately documented scoring-only retry, each run had 40 RAGAS scores. The mean of the three run means and **sample standard deviation across those run means** were: faithfulness **0.7417 ± 0.0520**, answer relevancy **0.5720 ± 0.0247**, and reference-based context precision **0.9492 ± 0.0105**. These are three repeated measurements on the same author-labelled fixture, not 120 independent users, human review, a confidence interval or a production estimate.

All 120 HTTP calls returned 200. The initial scorer pass completed 40/40/39 because run 3 case H08 had a provider connection error; a separate retry of the identical saved answer and context yielded the 40th score. The error is retained. In the three runs, 6/27, 4/27 and 5/27 cases labelled directly answerable received `insufficient_evidence`, potential false refusals requiring adjudication. A same-seed direct-model probe produced two different responses in three requests. The seed was sent via the evaluation wrapper, not configured as a general production feature, and provider determinism is not guaranteed.

See the [per-run table and interview questions](reproducibility-interview-qa.md#repeated-live-evaluation-recorded-results) and [public run artifacts](https://github.com/neeraj1909/xai-rag/tree/main/evals/results/2026-11-20-seeded-repeated). The earlier 40-case aggregate below used a different source snapshot and judge, so differences should not be attributed solely to repeatability or the seed.

## Grounding: standalone synthetic verifier probe

The 20 November 2026 probe used the frozen 50-case fictional fixture SHA-256 `c7efa755984497cf9f47a5cc9d7f660187e0e391951cdb47330b434ba0b227ce`, author-created expected outcomes and the `gpt-6-luna` API alias. A probe plus the full run made 51 successful calls. The model page listed no dated snapshot, so the alias may change.

| Checker | Slice | False accepts | False rejects | API errors |
| --- | ---: | ---: | ---: | ---: |
| Luna judge | Original 42 cases | 0 | 0 | 0 |
| Luna judge | 8 injection cases | 0 | 0 | 0 |
| Local NLI AND Luna judge | Original 42 cases | 0 | 2 | 0 |

The original NLI on the 42-case slice produced one false accept and two false rejects. On case N12 the NLI incorrectly accepted an unsupported universal claim with score 0.9043; the judge returned insufficient evidence. The judge also differed from the authors on contradiction versus insufficient evidence for two blocked cases; those labels themselves require independent adjudication. Its 50-case median request latency was 1.203 seconds, with four concurrent requests. The 51 calls consumed 10,875 input and 1,898 output tokens, estimated at $0.0020365 at the listed standard rates, excluding tax or negotiated pricing. These are not full application latency or costs. The fixture is small, synthetic, not independently labelled and not a production reliability estimate.

The standalone probe did not exercise real provider failure handling or the end-to-end answer-release path. Separate integration-unit tests used a real OpenAI SDK against a local HTTP mock and observed that malformed or truncated outputs, empty choices and provider errors were withheld by the service. A mock does not measure actual provider availability. The mandatory gate is fallible, can omit material facts and transfers bounded visible evidence to the judge provider. The API generator token counters do not include the separate judge request.

## Crash and replay: real disposable stores

A local synthetic test used Chroma 1.5.9, Elasticsearch 8.17.0, synthetic 384-dimensional vectors and no provider calls. A child process intentionally exited after writing Chroma and before writing Elasticsearch. The original source file was then changed. A fresh process recovered the saved original bytes and checked actual content and metadata against the intended manifest: one Chroma and one Elasticsearch record matched.

Do not omit the two previous attempts: the first failed before writing because an isolated branch had an outdated tenant-store interface; the second reached the forced exit but timed out as Elasticsearch created an index. The passing attempt used a 60-second client timeout and disabled the disk watermark only on the disposable test Elasticsearch node, whose host was over 90% full. Both owned containers were removed and their ports were closed. This demonstrates one crash boundary, not multi-host recovery, atomic reads, production storage durability, delayed remote-write fencing, or vector correctness.

After the journal directory-fsync fix, the forced-crash and replay scenario was [repeated on the final development source](evaluation/hardening-2026-11-20/recovery-final/README.md): the private, pre-provisioned journal recovered original staged bytes after source mutation and actual content/metadata parity was 1/1. Python file hashes were unchanged during that run; owned containers were removed and ports were free. The repeat again used a 60-second test-client timeout and a disk-watermark override only on disposable Elasticsearch. A process-crash test does not itself simulate power loss or prove that delayed remote writes are fenced. Each source hash list identifies the development files for that run, not an entire deployable image.

The harness did not archive its dirty source at run time. A later [reconstructed Python source snapshot](evaluation/hardening-2026-11-20/evaluated-python-source/README.md) matches the recorded tree digest, but does not preserve the full deployment, dependencies or data; HEAD alone cannot reproduce this run, and later code changes are not covered by its scores. Generator, grounding judge, RAGAS LLM and security judge used the `gpt-6-luna` alias; RAGAS embeddings used `text-embedding-3-small`. Model aliases can drift. The manifest records model revisions and settings. The [archive](evaluation/hardening-2026-11-20/http/README.md) contains the fixtures, per-case captures, results and budgets, but excludes temporary credentials and policy files.

The quality fixture SHA-256 is `b666492a41e218d6fefa0fcca0fa6ab26277bfb7dfba34413ffadb672afdc8cf`; all **40/40** planned requests returned HTTP 200 and captured prompt-visible evidence. HTTP 200 is not an answer-quality pass.

A 350-attempt shared provider cap stopped the original RAGAS run: **15 cases computed, one failed at the cap and 24 were unscored**. The project evaluator's citation-validity score of 1.0 checks that cited IDs were visible to the generator; it does **not** establish source support or factual truth. Exact-string answer match was 0 under its formatting-sensitive comparison and should not be read as a semantic correctness score. Source-level labels were not invented as chunk-level relevance labels, so unavailable retrieval metrics remain unscored.

The separate security fixture SHA-256 is `851007eca4123773a57a4003378dbf8d85c82784fd81376d5b26f341a7a7cc3e`; **28/28** security requests returned HTTP 200 and all case-specific source sets were visible to the generator. The combined known-token estimate is approximately **$0.08375**, excluding any charges for calls with missing usage, taxes or negotiated pricing; it is not an invoice. ## Bilingual NLI pair diagnostic and adaptive judge studies

A frozen **30-pair** author-labelled synthetic probe compared the configured English NLI model `MoritzLaurer/DeBERTa-v3-base-mnli-fever-anli` with the pinned multilingual candidate `MoritzLaurer/mDeBERTa-v3-base-mnli-xnli`, both at the existing 0.5 threshold. Each completed 15 English, 12 Hindi and three romanized Hindi pairs; these are premise/claim pairs, not full HTTP requests or human review. On this fixture the English model had one Hindi false accept and two Hindi false rejects; the multilingual candidate had no errors on those 12 Hindi pairs but one false accept on the three romanized Hindi pairs. Both had at least one false accept overall. This tiny, authored, non-representative set does not justify a model swap or establish multilingual quality. The candidate's model, revision, resource usage, scores, exact fixture and script are in the [NLI diagnostic archive](evaluation/hardening-2026-11-20/nli-diagnostic/README.md).

In a separate safety/relevance fixture, the configured NLI returned `supported` on three instruction-like claims. That does **not** itself mean NLI failed its intended task: NLI estimates textual entailment, not whether an instruction is safe, relevant or authorized. A judge can make the same distinction incorrectly, so the service must not treat support as a safety decision. The three probes were not an end-to-end HTTP exploit demonstration. See [per-pair scores](evaluation/hardening-2026-11-20/nli-diagnostic/attack-pairs.json).

A question-aware judge prompt was compared with an earlier candidate on 25 fictional, adaptively selected cases. Across 50 successful calls, the baseline had three expected-release false accepts and the earlier question-aware candidate had two; neither had a false reject on this small set. Both accepted an imperative case contrary to the fixture's combined relevance/safety label. **That earlier candidate was rejected**, not adopted on the strength of these scores. The result does not establish a real-world failure rate. [Paired results and limitations](evaluation/hardening-2026-11-20/judge-question-candidate/README.md).

An additional safety-and-coverage judge probe recorded 25/25 expected binary decisions on a separate **adaptive, author-labelled** fixture. An earlier coverage-only probe first had 24/24 authentication failures on an inherited endpoint; after switching to the official endpoint it made 24/24 successful decisions against that fixture's coverage labels. These controlled probes are not blind holdouts or human review; 25/25 is not proof of safety or completeness. They do not establish how a later full pipeline will behave. Preserve the [sanitized failed-attempt records](evaluation/hardening-2026-11-20/coverage-judge/attempts.jsonl), [successful coverage results](evaluation/hardening-2026-11-20/coverage-judge/summary-official.json), and [safety-and-coverage summary](evaluation/hardening-2026-11-20/safety-coverage/summary.json), and independently evaluate new prompts and the full pipeline before claiming improvement.

## Later safety/coverage candidate: REST and SSE

A safety-and-coverage candidate, subsequently integrated into the development checkout, was exercised on **10 adaptively selected fictional cases over both REST and SSE**, for **20/20 HTTP 200**. All required case-specific source sets were visible in the capture, with no unauthorized source metadata observed. Across the ten SSE cases, the recorded events contained no captured generated candidate claim before generation. The test did not force the previous probes' exact claims into the generator, so it cannot prove those attacks reproduced or were fixed. It is not independently human-reviewed, blind or representative of production traffic.

The partially answerable `benign-03` case and the same-scope conflicting `conf-01` case were refused; the date-scoped `conf-02` REST request produced its 2025 answer. Other cases had mixed outcomes, and partial-answer utility remains unresolved. The run used the `gpt-6-luna` alias for generation and judging, made 38 successful paid calls (20 generation, 18 judging), and reported 18,312 input and 5,991 output tokens, estimated at $0.0048267 under the experiment's standard rates. ## Transport failure investigation

A separate short loopback experiment tested a timing hypothesis with a FastAPI/Uvicorn stub, not the XAI-RAG application or actual stores. With httpx's default pooled client expiry and Uvicorn keepalive both at five seconds, five-second probes saw **8/49 readiness errors and 3/9 synthetic query errors**. A parallel client using `Connection: close` saw **0/49 and 0/9** respectively. In a separate later run with server keepalive increased from 5 to 15 seconds, both pooled and connection-close arms saw **0/49 and 0/9**. The runs were short and sequential, not randomized. The original failing arm reported `ReadError` or `RemoteProtocolError`. This shows a possible local pooling boundary, not that it caused the earlier app soak's two unexplained errors, nor that switching all production traffic to connection-close is appropriate. The Dockerfile now configures its Uvicorn process with `--timeout-keep-alive 15`; this can increase idle socket/file-descriptor retention and does not configure other runtimes or proxies. The Docker healthcheck uses a fresh `urllib` request and is not this shared httpx pool. The [per-request events, script and conditions](evaluation/hardening-2026-11-20/transport-boundary/README.md) are retained; validate actual client/server settings and production network behavior independently.

## Literal evidence false refusal in final validation

A local E2E attempt with an OpenAI-compatible **stub** produced a claim copied verbatim from its cited Markdown source, but the NLI gate returned `not_supported`; the API consequently returned `insufficient_evidence` and withheld the answer. A separate probe on that one claim returned entailment/contradiction **0.0443/0.8765** for the original Markdown chunk, **0.9932/0.0013** for the sentence alone, and **0.9902/0.0022** for a plain heading plus the sentence. These differences indicate possible context or formatting sensitivity in this example, not a proven root cause or a measured overall failure rate. Preserve this false refusal and evaluate possible repairs on an independently labelled set; do not bypass verification to force a passing demo. The [selected claim, cited context and scores](evaluation/hardening-2026-11-20/nli-literal-e2e/README.md) exclude credentials and unrelated log content.

## Final local black-box E2E

A later final-development local validation passed **one black-box test in 84.63 seconds** on a simple single-sentence source. It exercised scoped ingestion and replay, REST, SSE and four simultaneous queries (p50 **27.10 s**, maximum **35.00 s** across those four). Separate probes returned 401 for an unauthenticated query and 403 for ungranted or reader ingestion; empty-grant and other-tenant queries returned no sources or explanations. These few checks are not a production-capacity or comprehensive security assessment.

This result used real disposable Chroma/Elasticsearch and real NLI, with a deterministic provider stub. The API image was a **current-source overlay on a pre-existing dependency image**, not a fresh build of the repository Dockerfile; a test wrapper started Uvicorn with 15-second keepalive. The isolated ES cluster had its disk watermark disabled for this test. The first attempt failed while the offline reranker was unavailable, and a later attempt on the original Markdown sample failed because the gate refused a literal supporting claim; the final passing run used a simpler source and does not erase either failure. [Manifest, all three outcomes, authorization checks and cleanup](evaluation/hardening-2026-11-20/final-e2e/README.md). Full clean-image reproducibility and the Markdown false refusal remain separate limitations.
